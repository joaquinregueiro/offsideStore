# Delta al ERD v1.3 — 2026-09-10

Cambios de esquema y semillas que **el ERD todavía no refleja**, para que el
owner los lleve a `docs/04-technical/database-design.md` (solo lectura desde el
código, CLAUDE.md §3). Hasta que eso pase, **ERD y schema de Drizzle no
coinciden** en lo que se lista acá.

> Este documento tiene **dos partes**: el primer delta (§1–§8, migraciones
> `0009`/`0010`) y el **segundo delta** (§9–§16, migración `0011`), pedido
> por el owner en la misma conversación y aplicado en la ola siguiente.
> Después de los dos: **55 tablas, 38 enums**.

> Los dos cambios arquitectónicos los **autorizó el owner en la conversación
> del 2026-09-10**: publicaciones promocionadas con comisión mayor, y —al pedir
> "todas las funciones de Mercado Libre"— preguntas y respuestas en la ficha.
> Nada de esto se decidió desde el código (CLAUDE.md §5).

Migraciones: `0009_promociones_y_preguntas.sql` (esquema, generada por
drizzle-kit) y `0010_seed_tiers_y_ciclo_de_orden.sql` (datos, escrita a mano
como 0003–0007). Aplicadas en `offside_dev` y `offside_test`. `db:check` sin
drift; **257/257** de integración, **299/299** unitarios, typecheck, lint y
Prettier en verde.

Después de esto: **53 tablas, 38 enums**. Ningún enum nuevo.

## 1. `listings` — dos columnas y un índice (§9.1)

| Columna          | Tipo        | Null | Default | Notas                                                                   |
| ---------------- | ----------- | ---- | ------- | ----------------------------------------------------------------------- |
| `promoted_until` | timestamptz | sí   |         | La publicación está **promocionada mientras `now() < promoted_until`**. |
| `promoted_at`    | timestamptz | sí   |         | Última vez que se promocionó. Solo trazabilidad.                        |

Índice: `INDEX(promoted_until) WHERE promoted_until IS NOT NULL`
(`listings_promoted_until_idx`). Parcial porque la inmensa mayoría de las filas
tendrá NULL; la vitrina y la búsqueda consultan `promoted_until > now()`.

**Decisión de diseño:** la promoción es un **predicado derivado**, no un estado.
No toca `listings.status` y al vencer no hay nada que "despromocionar": la fila
queda como evidencia. Es el mismo criterio que el vendedor desconectado
(SS-013, CLAUDE.md §19). La duración y el multiplicador salen del Config Store
(`promotion_duration_days`, `promotion_commission_multiplier`); en la fila se
guarda el instante ya calculado, igual que `orders.payment_deadline`.

## 2. `orders` — una columna (§11.1)

| Columna                               | Tipo         | Null | Notas                                                                                       |
| ------------------------------------- | ------------ | ---- | ------------------------------------------------------------------------------------------- |
| `promotion_multiplier_at_transaction` | numeric(6,3) | sí   | **Snapshot** (DEC-030). Multiplicador de comisión aplicado por promoción. Null = no aplicó. |

Pertenece al snapshot financiero: sin esto `commission_rate_at_transaction`
diría "18%" y nadie podría explicar por qué esa orden pagó el triple que la de
al lado. **Nunca se recalcula** con el multiplicador vigente. Se guarda `null`
y no `1` cuando no hubo promoción, para distinguir "no aplicó" de "aplicó ×1".

`seller_tier_code_at_transaction` **ya existía** y hoy nadie la escribe. No se
tocó: el módulo de tiers la tiene que empezar a llenar.

## 3. Tabla nueva `listing_questions` (módulo nuevo, sin sección en el ERD)

Preguntas y respuestas públicas en la ficha de una publicación. Modelo de
**pregunta con una respuesta**, como Mercado Libre: no es un hilo ni un chat
(BR-053 marca la mensajería in-app como 🟡 futura).

| Columna       | Tipo        | Null | Default           | Notas                                                                                                                           |
| ------------- | ----------- | ---- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `id`          | uuid        | no   | gen_random_uuid() | PK                                                                                                                              |
| `listing_id`  | uuid        | no   |                   | FK→listings **RESTRICT**                                                                                                        |
| `asker_id`    | uuid        | no   |                   | FK→users **RESTRICT**. Nunca el dueño de la publicación (app).                                                                  |
| `question`    | text        | no   |                   |                                                                                                                                 |
| `answer`      | text        | sí   |                   | Null mientras `status='open'`.                                                                                                  |
| `answered_at` | timestamptz | sí   |                   |                                                                                                                                 |
| `answered_by` | uuid        | sí   |                   | FK→users **RESTRICT**. `users.id`, no `seller_profiles.id`, para que el día que responda moderación no haga falta otra columna. |
| `status`      | text        | no   | `'open'`          | `open` \| `answered` \| `hidden`. **CHECK** con los tres valores.                                                               |
| `created_at`  | timestamptz | no   | now()             |                                                                                                                                 |
| `deleted_at`  | timestamptz | sí   |                   | Soft delete (§20.10).                                                                                                           |

Índices: `INDEX(listing_id)`, `INDEX(asker_id)`.
CHECK: `listing_questions_status_check` — `status IN ('open','answered','hidden')`.

**Por qué `text` y no un enum de dominio:** agregar un valor a un `pgEnum` es
un cambio de esquema (CLAUDE.md §5) y el vocabulario de moderación de preguntas
no está decidido. El CHECK evita que un typo invente un cuarto estado en
silencio; ampliarlo sigue siendo una migración, pero una trivial.

**Por qué RESTRICT en las tres FK:** una pregunta es evidencia de lo que se
dijo antes de una compra (útil en una disputa) y no debe desaparecer porque
alguien borre su cuenta o su publicación —que además son soft delete—.

En Drizzle: `packages/database/src/schema/questions.ts`, exportada desde
`index.ts`, con `listingQuestionsRelations` en `relations.ts` (`listing`,
`asker`, `answeredByUser`; las dos relaciones con `users` llevan
`relationName`), `listings.questions` y `users.questionsAsked`.

Para el ERD §24: agregar `listing_questions` a la lista (53 tablas).

## 4. Semillas — `seller_tiers` (§7.1)

El ERD dice "no se seedean valores hasta definir DEC-037 (🟦)". El owner pidió
**niveles de vendedor con comisión decreciente** el 2026-09-10: esa es la
definición que faltaba. Tres filas activas:

| `code`        | `name`               | `commission_rate` | `limits`                    | `benefits.description`                                        |
| ------------- | -------------------- | ----------------- | --------------------------- | ------------------------------------------------------------- |
| `INICIAL`     | Vendedor inicial     | `0.0600`          | `{"minCompletedSales": 0}`  | Comisión estándar de la plataforma. Es el punto de partida.   |
| `AVANZADO`    | Vendedor avanzado    | `0.0500`          | `{"minCompletedSales": 10}` | Un punto menos de comisión a partir de 10 ventas completadas. |
| `PROFESIONAL` | Vendedor profesional | `0.0400`          | `{"minCompletedSales": 50}` | La comisión más baja de la plataforma a partir de 50 ventas.  |

⚠️ **UNIDAD.** `seller_tiers.commission_rate` es `numeric(6,4)`: una
**fracción** (`0.0600` = 6%), igual que `orders.commission_rate_at_transaction`.
**No** son basis points como `app_settings.commission_rate_default` (`600`): en
`numeric(6,4)` el máximo es 99.9999 y 600 no entra. Quien lea el tier y
necesite basis points hace `round(rate * 10000)`; quien escriba el snapshot de
la orden copia la fracción tal cual (`basisPointsToRateSnapshot()` en
`modules/config/services/settings.service.ts` hace la conversión inversa).

⚠️ **Los codes no salen de la doc**: DEC-015 solo da ejemplos "conceptuales, no
definitivos" (`SELLER_STANDARD/VERIFIED/FEATURED/STORE`), y esos describen
tipos de cuenta, no una progresión por volumen. SS-015: esto **no** es el USER
LEVEL ni el estado de riesgo.

⚠️ **No asigna tiers a nadie.** `seller_profiles.seller_tier_id` sigue NULL
(= sin tier, DEC-037) y el sistema sigue cobrando `commission_rate_default`.
El 6% de INICIAL coincide con ese default a propósito: asignar el tier inicial
no cambia lo que cobra nadie.

## 7. Decisiones asumidas — pendientes de confirmación del owner

1. **Todos los valores numéricos** de §4 y §5 (6/5/4 %, 0/10/50 ventas, 48 h,
   72 h, 7 d, 30 d, ×3, 7 d, boost 1, 3 d, pesos de reputación). Se cambian
   desde Admin insertando una versión nueva; ninguno está en código.
2. Los **codes** `INICIAL / AVANZADO / PROFESIONAL`.
3. Que el umbral de tier cuente **solo `COMPLETED`** y excluya reembolsadas.
4. `value_type` con la convención del código (`number`/`json`/`bool`) en vez de
   la del ERD (`int`/`duration`).
5. El **CHECK** sobre `listing_questions.status`: no estaba en el pedido, se
   agregó por seguridad. Quitarlo es una migración de una línea.
6. `promotion_multiplier_at_transaction` **null** cuando no hay promoción, en
   vez de `1`.
7. La promoción como **predicado derivado** sobre `promoted_until`, sin
   estado propio ni tabla de historial de promociones. Si el negocio necesita
   cobrar la promoción o auditar cuántas veces se promocionó algo, va a hacer
   falta una tabla (`listing_promotions`) — eso sería otro cambio arquitectónico.

## 8. Lo que este delta NO resuelve

- **`promotion_rank_boost` no tiene escala definida**: el módulo de búsqueda
  decide si es un sumando al `ts_rank` o un factor. La clave existe para que
  el peso no quede hardcodeado (PS-021 ⚙️).
- **Quién puede ocultar una pregunta** (`hidden`) depende de una capacidad
  nueva en el mapa de DEC-023; `MODERATOR` sigue sin capacidades.
- **Cobrar la promoción**: el owner autorizó "comisión mayor", no un pago
  anticipado. No hay tabla de cobros de promoción.
- El ERD `docs/04-technical/database-design.md` sigue en v1.3: §9.1, §11.1,
  §24 y una sección nueva para `listing_questions` esperan la edición del
  owner.

# Segundo delta — migración `0011_promociones_envio_y_reportes`

Completa lo que el plan de producto pide y `0009`/`0010` no cubrieron. **Todo
lo autorizó el owner en la conversación del 2026-09-10** (CLAUDE.md §5): dos
tablas nuevas, siete columnas en cuatro tablas existentes y nueve claves de
`app_settings`.

**Una sola migración**, a propósito: la parte de esquema la generó
`drizzle-kit generate` (con `0011_snapshot.json`) y las semillas se agregaron
a mano **al final del mismo archivo**, separadas por `statement-breakpoint` y
con el mismo `INSERT … WHERE NOT EXISTS` idempotente de `0003`–`0007` y
`0010`. Las claves describen columnas que la misma migración crea; no tiene
sentido que exista una sin la otra.

⚠️ **Detalle del journal que importa:** el `when` de `0011` se fijó en
`1789264153605` (= `0010` + 24 h), **no** en el `Date.now()` que puso
drizzle-kit. `0010` se había registrado con un `when` en el futuro (`0009` +
24 h), y el migrador de Drizzle aplica una entrada **solo si su `when` es mayor
que el de la última aplicada**: con el valor generado, `0011` habría quedado
**silenciosamente sin aplicar** en toda base que ya tuviera `0010`. Quien
agregue `0012` tiene que seguir por encima de ese número.

Verificado: `db:check` sin drift; `db:generate` no produce nada; migradas
`offside_test`, `offside_dev` y una base propia de la ola
(`offside_test_esquema`): **55 tablas, 38 enums, 12 migraciones** en las tres.
**257/257** de integración existentes sobre la base migrada, más **9 nuevos**
en `packages/database/src/erd-delta-2026-09-10.integration.test.ts` que fijan
cada CHECK, UNIQUE y FK RESTRICT de este delta; **299/299** unitarios; eslint,
tsc y Prettier en verde sobre los archivos tocados.

## 9. Tabla nueva `listing_promotions` (historial de promociones)

`packages/database/src/schema/promotions.ts`. El §7.7 del primer delta dejó
anotado que auditar cuántas veces se promocionó algo iba a necesitar esta
tabla; el owner la pidió. **`listings.promoted_until` sigue siendo la
proyección rápida** (vitrina y búsqueda solo miran esa columna) y esta tabla
es el historial: una fila por cada promoción. Se escriben en la misma
transacción; si difieren, manda el historial.

| Columna                          | Tipo         | Null | Default           | Notas                                                                                           |
| -------------------------------- | ------------ | ---- | ----------------- | ----------------------------------------------------------------------------------------------- |
| `id`                             | uuid         | no   | gen_random_uuid() | PK                                                                                              |
| `listing_id`                     | uuid         | no   |                   | FK→listings **RESTRICT**                                                                        |
| `seller_id`                      | uuid         | no   |                   | FK→seller_profiles **RESTRICT**. Redundante con `listings.seller_id` a propósito (consulta).    |
| `status`                         | text         | no   |                   | `active` \| `ended` \| `cancelled`. **CHECK**.                                                  |
| `commission_multiplier_snapshot` | numeric(6,3) | no   |                   | Multiplicador **prometido al promocionar**. **CHECK** `> 0`.                                    |
| `starts_at`                      | timestamptz  | no   |                   |                                                                                                 |
| `ends_at`                        | timestamptz  | no   |                   | Instante ya calculado (`starts_at + promotion_duration_days`). **CHECK** `ends_at > starts_at`. |
| `cancelled_at`                   | timestamptz  | sí   |                   | Solo con `status='cancelled'`.                                                                  |
| `created_by`                     | uuid         | no   |                   | FK→users **RESTRICT**. `users.id`, no `seller_profiles.id`.                                     |
| `created_at`                     | timestamptz  | no   | now()             |                                                                                                 |

Índices: `INDEX(listing_id, status)`, `INDEX(ends_at)` (el barrido
`active → ended` recorre por vencimiento).

**Por qué `commission_multiplier_snapshot` no es redundante con
`orders.promotion_multiplier_at_transaction`:** acá queda lo que se le
prometió al vendedor cuando aceptó promocionar; en la orden, lo que se cobró.
Si un admin cambia `promotion_commission_multiplier` a mitad de una promoción,
**la orden copia este snapshot y no el valor nuevo** (DEC-030): el vendedor
aceptó ×3, no "lo que valga cuando alguien compre".

## 10. `orders` — dos columnas (§11.1)

| Columna                | Tipo | Null | Default     | Notas                                                                                 |
| ---------------------- | ---- | ---- | ----------- | ------------------------------------------------------------------------------------- |
| `commission_source`    | text | no   | `'default'` | `default` \| `seller_tier` \| `promoted`. **CHECK** `orders_commission_source_check`. |
| `listing_promotion_id` | uuid | sí   |             | FK→listing_promotions **RESTRICT**. Null salvo `commission_source='promoted'`.        |

Junto con `seller_tier_code_at_transaction` (ya existía) y
`promotion_multiplier_at_transaction` (§2) dejan escrito **por qué** la
comisión fue la que fue, sin reconstruirlo desde la config de entonces:

- `default` → `app_settings.commission_rate_default`; el vendedor no tenía tier
- `seller_tier` → `seller_tiers.commission_rate` del tier vigente
- `promoted` → la base (tier o global) × la promoción; `listing_promotion_id`
  dice cuál

RESTRICT en `listing_promotion_id`: borrar la promoción dejaría una orden que
dice "promoted" sin poder decir por cuál. Hay test.

## 11. `listings` — envío declarado (§9.1)

| Columna                | Tipo   | Null | Default      | Notas                                                                      |
| ---------------------- | ------ | ---- | ------------ | -------------------------------------------------------------------------- |
| `shipping_mode`        | text   | no   | `'to_agree'` | `included` \| `buyer_pays` \| `to_agree` \| `pickup`. **CHECK**.           |
| `shipping_cost_amount` | bigint | sí   |              | Centavos. **CHECK** `IS NULL OR >= 0`. Obligatorio en app si `buyer_pays`. |

Sin Correo Argentino no hay cotización (SH-011) y `shipping.md` §5.b deja
"quién paga" y "retiro presencial" 🟡: el envío lo **declara quien vende** y
el importe se congela en `orders.shipping_amount` (ya existía) al crear la
orden, igual que el precio (BR-023 / DEC-030).

**Que `shipping_cost_amount` sea obligatorio con `buyer_pays` se valida en la
app, no por CHECK**: en un mismo formulario el modo puede cambiar antes que el
importe, y un CHECK cruzado rechazaría estados intermedios legítimos de un
`UPDATE` parcial.

## 12. `seller_profiles.vacation_until` (§7.2)

`timestamptz NULL`. Modo vacaciones: el vendedor está ausente **mientras
`now() < vacation_until`**. Es un **predicado derivado**, no un estado: no toca
`listings.status` ni `seller_profiles.status`, y al vencer no hay nada que
reactivar. Misma lógica que la desconexión de Mercado Pago (SS-013, CLAUDE.md
§19): si se materializara `paused`, al volver sería imposible distinguir lo
que el vendedor pausó a mano (SS-050) de lo que apagó la ausencia.

## 13. `reviews.seller_reply` / `seller_replied_at` (§15)

`text NULL` / `timestamptz NULL`. Respuesta **pública** del vendedor a la
reseña. La reseña sigue siendo **unidireccional** —solo el comprador califica y
`rating` es suyo—; esto es un descargo que se muestra al lado. Va en la misma
fila porque hay a lo sumo una y no es un hilo (BR-053). **No emite
`user_history_events` ni entra en `seller_reputations`**: responder no cambia
la nota.

## 14. Tabla nueva `listing_reports` (denuncias de publicaciones)

`packages/database/src/schema/reports.ts`. `trust-and-safety.md` habla de
"marcas/flags de autenticidad dudosa", pero el ERD no modeló de dónde salen
cuando las hace **una persona**: `risk_events` es interpretación del sistema
(DEC-040), no una denuncia.

| Columna       | Tipo        | Null | Default           | Notas                                           |
| ------------- | ----------- | ---- | ----------------- | ----------------------------------------------- |
| `id`          | uuid        | no   | gen_random_uuid() | PK                                              |
| `listing_id`  | uuid        | no   |                   | FK→listings **RESTRICT**                        |
| `reporter_id` | uuid        | no   |                   | FK→users **RESTRICT**. Nunca el dueño (app).    |
| `reason`      | text        | no   |                   | Motivo, de una lista que valida la app.         |
| `note`        | text        | sí   |                   | Texto libre.                                    |
| `status`      | text        | no   | `'open'`          | `open` \| `reviewed` \| `dismissed`. **CHECK**. |
| `reviewed_by` | uuid        | sí   |                   | FK→users **RESTRICT**.                          |
| `reviewed_at` | timestamptz | sí   |                   |                                                 |
| `created_at`  | timestamptz | no   | now()             |                                                 |

Índices: **UNIQUE(listing_id, reporter_id)** — una persona denuncia una
publicación **una vez**; sin esto un solo usuario haría que una publicación
parezca denunciada por cien—, `INDEX(status)` (la cola de moderación).

`reason` es `text` **sin CHECK**: el vocabulario de motivos es de producto y
no está decidido; fijarlo en el esquema sería inventarlo. Sin `deleted_at`:
una denuncia no se borra, se descarta (`dismissed`) y queda.

⚠️ Resolver una denuncia exige una **capacidad de moderación nueva** en
`lib/permissions.ts` (DEC-023); `MODERATOR` sigue sin ninguna.
